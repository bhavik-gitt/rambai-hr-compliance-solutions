# Consultation enquiry backend integration specification

This document defines the future server contract for the existing RAMBAI consultation form. No backend, database, email sender, or WhatsApp Business integration is implemented in the frontend.

## Frontend configuration

Set the full public endpoint URL at build time:

```bash
VITE_ENQUIRY_API_ENDPOINT=https://api.example.com/v1/enquiries
```

This URL is not a secret. Do not add email credentials, WhatsApp access tokens, provider API keys, signing secrets, or private headers to any `VITE_` variable because Vite exposes those values to browsers.

The API must allow requests from the website's production origin and should reject unexpected origins.

## Request

**Method:** `POST`  
**Content-Type:** `application/json`

```json
{
  "fullName": "Visitor name",
  "companyName": "Organisation name",
  "email": "visitor@example.com",
  "phone": "+91 0000000000",
  "city": "Ahmedabad",
  "serviceRequired": "Payroll Management",
  "message": "The visitor's business requirements.",
  "submittedAt": "2026-11-02T07:30:00.000Z"
}
```

`submittedAt` is generated by the browser after client-side validation and uses ISO 8601 UTC format. The backend should also record its own receipt time and must not treat the browser timestamp as authoritative.

### Field rules

| Field | Required | Notes |
| --- | --- | --- |
| `fullName` | Yes | Non-empty trimmed string |
| `companyName` | No | Trimmed string |
| `email` | Yes | Valid email address |
| `phone` | Yes | Valid contact number |
| `city` | No | Trimmed string |
| `serviceRequired` | Yes | Must be an allowed RAMBAI service |
| `message` | Yes | At least 10 characters after trimming |
| `submittedAt` | Yes | Valid ISO 8601 timestamp |

The backend must repeat validation and sanitisation. Client-side validation improves usability but is not a security boundary.

## Backend workflow

1. Validate content type, origin, request size, rate limits, and every enquiry field.
2. Generate a server-side enquiry reference and receipt timestamp.
3. Format and send the email described below to `info.rambai@gmail.com`.
4. Format and send the WhatsApp Business message described below through approved server-side credentials.
5. Return success only when the backend has accepted responsibility for both delivery actions.
6. Return a failure response when validation fails, delivery cannot be accepted, or only one delivery channel succeeds.

If the future backend uses a provider queue, `success: true` means both messages were durably accepted for delivery, not necessarily read by their recipients. If no durable queue exists, it should mean both provider requests succeeded.

Use an idempotency strategy or short-window duplicate detection server-side. The frontend prevents rapid duplicate clicks, but server-side protection is still required for retries and multiple browser sessions.

## Success response

Use a 2xx status and explicitly return `success: true`:

```json
{
  "success": true,
  "message": "Your enquiry has been received. RAMBAI will review your request.",
  "enquiryId": "server-generated-reference"
}
```

The frontend does not show success for an empty response, non-2xx response, invalid JSON response, or response without `success: true`.

## Failure response

Use an appropriate non-2xx status:

```json
{
  "success": false,
  "message": "Please review the highlighted information.",
  "code": "VALIDATION_ERROR",
  "fieldErrors": {
    "email": "Please enter a valid business email."
  }
}
```

Suggested status codes:

- `400` or `422` — invalid request or fields
- `429` — rate limited
- `500` — unexpected backend failure
- `502` or `503` — email or WhatsApp provider unavailable

Do not return provider credentials, internal stack traces, or sensitive diagnostic data.

## Email delivery specification

**Recipient:** `info.rambai@gmail.com`  
**Reply-To:** the visitor's validated `email`  
**Suggested subject:**

```text
[RAMBAI Website Enquiry] {serviceRequired} — {companyName or fullName}
```

**Suggested body:**

```text
New consultation enquiry

Enquiry reference: {server enquiry reference}
Received at: {server receipt time}
Submitted at: {submittedAt}

Full name: {fullName}
Company / organisation: {companyName or "Not provided"}
Business email: {email}
Phone: {phone}
City: {city or "Not provided"}
Service required: {serviceRequired}

Business requirements:
{message}

Source: RAMBAI website consultation form
```

Use escaped plain text or safely escaped HTML. Never interpolate unsanitised values into HTML markup.

## Automatic WhatsApp Business delivery specification

The future backend—not the browser—should authenticate with the approved WhatsApp Business provider.

```text
New RAMBAI website consultation enquiry

Reference: {server enquiry reference}
Name: {fullName}
Company: {companyName or "Not provided"}
Email: {email}
Phone: {phone}
City: {city or "Not provided"}
Service required: {serviceRequired}
Message: {message}
Submitted at: {submittedAt}
```

Provider templates, opt-in requirements, message length limits, and delivery policies must be handled by the backend integration.

## Direct WhatsApp contact remains separate

The existing **Continue on WhatsApp** action is a user-initiated `wa.me` link. It pre-fills the visitor's current form details and requires the visitor to confirm sending inside WhatsApp.

It does not call `submitEnquiry()`, does not indicate automatic delivery, and must remain available independently of future backend configuration.

## Security and operational requirements

- Keep all provider credentials and API keys server-side.
- Enforce HTTPS.
- Validate and sanitise all input again on the server.
- Apply CORS restrictions, rate limiting, request-size limits, and abuse protection.
- Avoid logging complete enquiry content unless access and retention are controlled.
- Define retention and deletion procedures for personal information.
- Monitor partial delivery failures without exposing provider details to visitors.
